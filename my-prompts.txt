● Value of Dapr in this demo

  Without Dapr, each service would need to know the network address of the next
  service, handle retries, serialise messages, and manage a connection to Redis
  directly. With Dapr, none of that is in the application code.

  What Dapr buys us here:

  - Decoupling — OrderReceiver calls dapr.PublishEventAsync("orderpubsub", 
    "orders", order). It has no idea that OrderProcessor exists, where it runs,
    or how many instances there are. The sidecar handles delivery.
  - Subscription without polling — OrderProcessor and OrderFulfillment don't
    poll a queue. They expose a plain HTTP POST endpoint; the Dapr sidecar calls
    it when a message arrives. The [Topic] attribute is the only Dapr-specific
    thing in the handler.
  - Transport abstraction — the component backing orderpubsub can be swapped
    from Redis to Azure Service Bus, RabbitMQ, Kafka, etc. by changing one YAML
    file. No code changes.
  - State without a DB driver — dapr.SaveStateAsync("orderstate", key, value) is
    the entire persistence call. The sidecar talks to Redis; the app doesn't
    import a Redis client.
  - Portability — components/local/ uses localhost:6379; components/k8s/ uses
    the in-cluster DNS name. The service binaries are identical in both
    environments.

  ---

  Where Redis is used

  Redis plays two distinct roles, both configured as Dapr components:

  Component: orderpubsub
  File: components/*/pubsub.yaml
  Role: Message broker — stores pub/sub messages in Redis Streams. When
  OrderReceiver publishes to the orders topic, the message sits in Redis until
  the OrderProcessor sidecar delivers it.
  ────────────────────────────────────────
  Component: orderstate
  File: components/*/statestore.yaml
  Role: State store — a simple key/value store. OrderProcessor writes order-{id}

  keys; OrderFulfillment writes fulfillment-{id} keys.

  In Kubernetes, a single Redis Deployment (deploy/redis.yaml) serves both
  roles, reachable at redis-master.dapr-demo.svc.cluster.local:6379. Locally,
  dapr init starts a Redis container for the same purpose.

  The services themselves never open a Redis connection — they only speak to
  their own Dapr sidecar over localhost HTTP (http://localhost:3500), and the
  sidecar does the rest.
